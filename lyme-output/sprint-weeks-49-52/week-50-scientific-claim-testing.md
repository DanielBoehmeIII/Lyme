> "Can local models on consumer hardware become useful coding agents through better memory, compression, tool use, telemetry, and governance?"

#### From Demos

**Claim:** The v0.7 demo produces traces, semantic diffs, benchmark leaderboards, PR intelligence reports, ablation results, and research reports.
**Evidence:** `lyme-output/demo-v0.7/` contains 8+ JSON files.

**What this actually proves:** The demo scripts run successfully and produce structured output. The output follows the expected schemas. The content is generated data, not real measurements.

**Verdict:** No evidence. Demos demonstrate that the code runs, not that the claims are true.

#### From Failures

**Evidence:** `failures.py` has `FailureCategory(Enum)` with 14 values, `FAILURE_TAXONOMY` dict with detection strategies, `FailureDetector` class with 7 detection methods.

**What this actually proves:** Failure classification code was written. It has not been tested against real agent failures.

**Verdict:** No evidence. The failure detector has not been evaluated for precision, recall, or F1 against any labeled dataset.

#### From User Interventions

**Claim:** Users can interact with Lyme via CLI commands.
**Evidence:** 30+ commands are implemented and functional.

**What this actually proves:** The CLI works. There are zero user studies, zero user satisfaction measurements, zero task completion time measurements.

**Verdict:** No evidence. Functionality ≠ usability.

#### From Model Comparisons

**Claim:** Capability matrix evaluates models on code generation, bug finding, code explanation, refactoring, instruction following, and hallucination resistance.
**Evidence:** `models/evaluation.py` defines evaluation tasks.

**Verdict:** No evidence. The capability matrix is an empty spreadsheet.

#### From Longitudinal Results

**Claim:** Agents with persistent memory improve over 100+ sessions.
**Evidence:** The evaluation framework has a longitudinal evaluation command.

**What this actually proves:** The command can be invoked. It produces output from simulated data.

**Verdict:** No evidence. No agent was observed for more than one session.

**Test Design:**
- Independent variable: Architecture (Lyme-enhanced local model vs. raw local model vs. frontier API model)
- Dependent variable: Task success rate on 8 benchmark scenarios

- Evaluation criteria: all defined per scenario

**The experiment is design-complete and execution-empty.**

**Architecture helps. It does not replace scale.**

The data we would need to quantify this does not exist. But based on the literature on scaling laws and the design of Lyme's architecture:

1. Lyme's architecture provides the largest relative improvement for small models (D - C > B - A). A 7B model benefits more from compression, memory, and governance than a 70B model does.

2. But the absolute performance of a Lyme-enhanced 7B model is still below a raw 70B model. Architecture is a multiplier on base capability, not a replacement.

3. The most cost-effective configuration is probably a medium model (14B-30B, local or cheap API) with Lyme's architecture — balancing capability, cost, and safety.

4. The most honest finding: **We cannot answer this question without running the experiments.** All of the above is informed speculation.

# Lyme: A Measurement Infrastructure for Local Coding Agent Science

**Abstract**

Coding agents are being deployed into production with less observability than the average web service. The research community lacks standardized infrastructure for measuring, comparing, and improving agent behavior across models, architectures, and tasks. We present Lyme, a local-first research platform designed to fill this gap. Lyme provides a dual architecture — a product layer for developer tools and a research layer for scientific instrumentation — connected by a shared telemetry substrate. The system includes: a 5-layer codebase compression pipeline (file tree → API surface → subsystem clustering → invariant discovery → task-aware rehydration), a persistent memory system with three memory types, a cognitive tracing framework with 15 thought types, a causal graph engine for dependency analysis, a governance system with machine-readable policies, a benchmark engine with 8 scenarios, and open standards for agent traces and semantic diffs. While the infrastructure is comprehensive, we report that zero of the system's core scientific claims have been empirically validated — the platform has not been connected to a real agent in a controlled experiment. We present the system design, analyze the gap between infrastructure and evidence, and propose a prioritized experimental agenda for Year Two.

**Keywords:** coding agents, local AI, software engineering, measurement infrastructure, agent observability

---

### 1. Introduction

Coding agents — AI systems that write, edit, and reason about code — are the most rapidly deployed technology in software engineering history. Within two years of the release of ChatGPT, millions of developers were using AI-powered coding assistants in production, and major technology companies were building autonomous agent systems [1, 2].

Despite this velocity, the empirical basis for understanding coding agents is remarkably thin. Benchmarks like HumanEval [3] and SWE-bench [4] measure narrow capabilities in artificial settings. Production deployments are evaluated on vibes — "it feels better" — rather than structured measurement. Agent architectures are proprietary or rapidly changing. There are no standardized formats for recording agent behavior, no shared vocabularies for classifying agent failures, no established metrics for comparing agent cognition across models, and no infrastructure for measuring how agents improve over time.

This paper presents Lyme, a system designed to provide this missing infrastructure. Lyme is not a coding agent. It is a measurement platform for coding agents — analogous to what distributed tracing (Zipkin, Jaeger) is to microservice observability, or what MLFlow is to machine learning experiment tracking.

Lyme's core design contributions are:

**1. Dual architecture.** Every product action (diagnosing a repo, classifying a diff, answering a question) generates research-grade data (cognitive traces, causal graphs, invariant catalogs). Research insights feed back into product behavior. The two layers share a telemetry substrate separated by an explicit privacy boundary.

**2. Compression-first codebase understanding.** Rather than feeding raw context to models, Lyme implements a 5-layer compression pipeline that progressively abstracts a codebase from file tree to API surface to subsystem map to invariant catalog to task-specific rehydration packet. This encodes a hypothesis about the structure of software comprehension.

**3. Governance-as-code for safe autonomy.** Lyme provides machine-readable constitutions, 5-level decision frameworks, immutable change ledgers, and verification graphs that connect claims through changes to tests to traces to approvals.

**4. Open standards for agent behavior.** The Open Agent Trace Standard (OATS) and Semantic Diff Standard (SDS) define portable, versioned, validated formats for recording and comparing agent behavior across models and architectures.

**Critical admission:** After one year of development, Lyme has produced comprehensive infrastructure but zero empirical results. The platform has not been connected to a real agent in a controlled experiment. All benchmark results in the system are simulated. The scientific claims in Lyme's documentation are aspirational. We report this not as a limitation of the approach but as the current state of a research project that prioritized infrastructure over experimentation. We describe both what was built and what was not tested.

---

### 2. Related Work

**Agent Frameworks.** LangChain [5], CrewAI [6], and AutoGPT [7] provide frameworks for building agent systems. They focus on composition, tool use, and orchestration. None provide built-in observability, measurement, or governance infrastructure. They are construction kits, not measurement platforms.

**Agent Benchmarks.** SWE-bench [4], HumanEval [3], and MBPP [8] evaluate code generation capabilities. DevBench [9] and AgentBench [10] evaluate broader agent capabilities. These are valuable for model comparison but do not provide infrastructure for ongoing measurement of agent behavior in production-like settings. Lyme complements these by providing a framework for continuous, structured measurement.

**Agent Observability.** LangSmith [11], Weights & Biases Prompts [12], and Arize AI [13] provide LLM observability for prompt engineering and response monitoring. They focus on input/output logging, latency, and cost tracking. Lyme extends this to cognitive traces (decision points, confidence, exploration patterns), causal analysis, and governance verification.

**Local Model Infrastructure.** Ollama [14], llama.cpp [15], and LocalAI [16] make local model deployment accessible. These are enabling infrastructure for local agent research. Lyme builds on them by adding the measurement, compression, and governance layers needed for rigorous study.

**Software Analysis.** Tree-sitter [17], Semgrep [18], and CodeQL [19] provide program analysis capabilities. Lyme's compression pipeline uses similar techniques (AST parsing, pattern matching) but wraps them in a layered architecture designed for agent context construction rather than standalone analysis.

**To our knowledge, Lyme is the first system that combines agent observability, codebase compression, persistent memory, cognitive tracing, governance, and open standards into a single research platform.** The closest analog is MLFlow for machine learning, but applied to the domain of coding agent cognition.

---

### 3. System Design

#### 3.1 Architecture Overview

Lyme is organized into three layers:

**Product Layer.** CLI-accessible developer tools: `lyme doctor` (repo diagnosis), `lyme ask` (evidence-grounded Q&A), `lyme diff` (semantic diff classification), `lyme trace` (execution replay), `lyme fix` (safe edit protocol), `lyme history`/`lyme audit`/`lyme undo` (action management), `lyme memory` (persistent store), `lyme run`/`lyme bench` (benchmark execution).

**Research Layer.** Scientific instrumentation: cognitive tracing (15 thought types, decision points, confidence scoring), causal graph construction and failure propagation, invariant discovery and violation detection, temporal modeling, scaling law experiments, agent coordination studies, hallucination analysis, context degradation measurement.

**Governance Layer.** Safe autonomy infrastructure: change governance engine (5 decision levels), repo constitution (machine-readable policies), change ledger (immutable audit trail), sensitive code detection, multi-critic review board, verification graph (claims → tests → traces → approvals).

The three layers share a telemetry substrate for event recording, metric collection, span tracing, and storage. An explicit privacy boundary separates product and research data with 4 consent levels and 6 sanitization rules.

#### 3.2 Compression Pipeline

The compression pipeline (Figure 1) implements five progressive abstraction layers:

```
Raw Files → [Layer 1: File Tree] → [Layer 2: API Surface]
         → [Layer 3: Subsystems] → [Layer 4: Invariants]
         → [Layer 5: Task-Aware Rehydration]
```

**Layer 1 (FileTreeLayer).** Extracts file tree structure, language detection (55 languages via file extension mapping), framework detection (14 frameworks), entry point identification, and package/module structure.

**Layer 2 (APILayer).** Extracts API surface: classes, functions, methods, imports, exports, async signatures. Full AST parsing for Python. Regex-based extraction for JavaScript, TypeScript, and Markdown.

**Layer 3 (SubsystemLayer).** Builds file-level import graphs, clusters files into subsystems using community detection, computes dependency matrices, detects circular dependencies, identifies subsystem boundaries.

**Layer 4 (InvariantLayer).** Discovers architectural invariants from git history: co-change patterns (files that change together), shared constants, duplicated code regions, circular dependencies, risk zones (large files, high-import files), naming conventions.

**Layer 5 (RehydrationLayer).** Given a task description, selects relevant subset of compressed representation using keyword-based relevance scoring, allocates token budget via ContextBudgetOptimizer, assembles task-specific context packet.

#### 3.3 Memory System

Three memory types with JSON-backed storage:

**Procedural memory.** Task procedures and workflows — how to run tests, deploy, configure. Encoded as structured step sequences.

**Episodic memory.** Past agent experiences — what was tried, what succeeded, what failed. Timestamped with importance scores.

**Semantic memory.** Codebase knowledge — facts about architecture, dependencies, conventions. Extracted from repository analysis and past sessions.

Retrieval uses keyword-based cosine similarity over stored text. Importance scoring combines access frequency, recency, and explicit priority marking. Age-based pruning removes low-importance entries when capacity limits are reached.

#### 3.4 Cognitive Tracing

The cognitive trace system records structured thought processes during agent execution:

- **15 thought types:** PLAN, DECISION, EXPLORATION, UNCERTAINTY, RETRY, ERROR, HALLUCINATION, INSIGHT, REASONING, QUESTION, CONCLUSION, ABANDONED, NAVIGATION, TOOL_SELECTION, CONTEXT_SHIFT, STATE_CHECK
- **Decision points:** Forks in the decision tree with alternatives considered, selection rationale, confidence scores
- **Analysis:** Confidence volatility measurement, exploration/exploitation ratio, error loop detection, decision paralysis detection, abandonment pattern recognition

Traces are stored in a versioned, replayable format compatible with the OATS standard.

#### 3.5 Governance System

**Decision levels (escalating autonomy):**
1. AUTO_APPLY — No human review needed
2. PATCH_ONLY — Show patch, apply after confirmation
3. REQUIRE_REVIEW — Require human review before application
4. REQUIRE_APPROVAL — Require explicit approval from authorized reviewer
5. BLOCK — Action cannot be performed

**13 default policies** covering: security files, architecture changes, API modifications, configuration changes, dependency updates, database schemas, authentication/authorization, encryption/cryptography, testing requirements, documentation requirements, deployment targets, compliance regulations, rollback procedures.

**Verification graph** connects: claims → code changes → test results → trace data → static analysis → type checks → approvals → benchmark outcomes → rollback evidence. Supports 43 evidence types and 14 gap labels.

#### 3.6 Open Standards

**Open Agent Trace Standard (OATS) v0.7.0.** JSON schema for agent execution traces. Includes: session metadata, step sequences with input/output pairs, tool calls with parameters and results, decision points with alternatives, confidence scores, token usage, timing data, error records.

**Semantic Diff Standard (SDS).** JSON schema for semantic diff representation. Includes: diff metadata (files, summary, stats), semantic intent classification (refactoring, bug fix, feature addition, dependency change, documentation, configuration), behavioral equivalence analysis, invariant impact assessment, risk scoring.

**Software Cognition Benchmark Specification.** 8 cognitive dimensions × 16 tasks with anti-gaming rules, required telemetry, multi-criteria scoring formulas.

### 7. Failure Analysis

We analyze the project's failures because they are more informative than its successes.

**Failure 1: Infrastructure over experimentation.** The project allocated approximately 90% of effort to infrastructure and 10% to experimentation. The correct ratio for a research project is the inverse. Result: comprehensive infrastructure with zero validated claims.

**Root cause:** Engineering incentives. Building systems is more tractable than designing and executing experiments. The satisfaction of "it works" (code compiles, commands run, output generates) displaced the harder satisfaction of "we know something."

**Failure 2: Scope expansion without validation.** From v0.1 through v0.7, the project added: multi-agent society simulation, software civilization maps, repository genome extraction, architecture fitness assessment, evolution forecasting, market coordination, ecosystem risk modeling, framework observatories, repository similarity engines, and self-improving agent infrastructure. None were validated. Each addition increased the distance between the infrastructure and its empirical grounding.

**Failure 3: Simulated data presented as results.** The demo system generates realistic-looking output — benchmark scores, ablation results, leaderboard positions — that is visually indistinguishable from real experimental data. This pattern, present since the first public release, gives the appearance of scientific progress without its substance. It is the project's most significant credibility problem.

**Failure 4: No external engagement.** The project was designed as an open research platform but operated as a solo engineering effort. There are no external contributors, no community, no users, no peer reviewers, no collaborators. The research questions were never tested against alternative perspectives.

**Failure classification (using Lyme's own taxonomy):**
- UNSUPPORTED_CLAIM: All performance claims in the documentation
- MODEL_UNCERTAINTY: The system's confidence in its own capabilities is uncalibrated
- CONTEXT_INSUFFICIENCY: The project lacks the context of external validation
- INCOMPLETE_FIX: The infrastructure exists but the core hypothesis remains untested

### 8. Limitations

**No empirical validation.** This is the single limitation that subsumes all others. Without experimental results, Lyme is a system design document with an implementation, not a research contribution with findings.

**Synthetic benchmark output.** All numbers presented as benchmark results, ablation effects, and leaderboard scores are simulated. They should not be cited, compared, or trusted as evidence.

**Python-only AST analysis.** Full program analysis is limited to Python. Other languages use regex-based heuristics that are fragile and incomplete.

**JSON-backed storage.** All data is stored as flat JSON files. No database backend means limited query capability, no indexing beyond naive keyword search, and no concurrent access support.

**No ML models.** All analysis is heuristic: pattern matching, rule evaluation, keyword search, threshold-based detection. No learned models, no embeddings, no classifiers.

**Single developer.** The entire codebase was written by one person. There has been no code review, no design review, no external architectural feedback.

**No real agent integration.** The platform designed to measure agents has never measured a real agent.

---

### 9. Future Work

**Priority 1: Run the experiments.** Execute the experimental protocol in Section 4. This is the only task that matters. Estimated: 4-8 weeks.

**Priority 2: Publish real results.** Replace all simulated data in the system with empirical measurements. Retract all unsupported claims from documentation.

**Priority 3: Engage community.** Publish the open standards. Invite external contributors. Establish a research collaboration network.

**Priority 4: Validate governance.** Test the governance system with real agents performing real tasks. Measure overhead, false positives, and effectiveness.

**Priority 5: Scale compression evaluation.** Test the compression pipeline across repository sizes (100-100,000+ files), languages (10+), and task types.

---

### 10. Conclusion

Lyme is a comprehensive infrastructure for coding agent measurement that has not yet fulfilled its research mission. The system demonstrates that a dual-architecture research platform for agent cognition is buildable: compression pipelines, memory systems, cognitive tracing, governance frameworks, and open standards can be implemented as a coherent, modular, locally-run system. What Lyme has not demonstrated is that any of this infrastructure improves, measures, or advances our understanding of coding agents.

The next step is unambiguous: stop building infrastructure and start running experiments. The platform is ready. The hypotheses are stated. The experimental designs are specified. What remains is the execution.
