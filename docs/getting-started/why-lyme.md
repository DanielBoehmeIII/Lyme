# Why Lyme?

## The Problem

Coding agents are the most important tools we do not understand.

We deploy them into production with less observability than the average web service.
We evaluate them on benchmarks that measure everything except what matters.
We treat them as black boxes and wonder why they behave unpredictably.

Existing tools optimize for one thing: task completion. They measure whether the
agent finished the task, not how it thought, where it struggled, or what it learned.

## What Lyme Does Differently

Lyme is built on three principles:

### 1. Observability > Speed

Every action is traced. Every decision is recorded. Every claim is grounded in
evidence. When something goes wrong, you can replay the agent's entire thought
process and see exactly where it failed.

### 2. Measurement > Demo

Lyme measures cognition — decision quality, context utilization, hallucination
frequency, recovery behavior, and confidence calibration. Not just task completion
rates and latency numbers.

### 3. Local > Cloud

Your code never leaves your machine. All traces, benchmarks, and measurements
stay local. Research data is anonymized and opt-in. Lyme is built for teams that
take code security seriously.

## Who Should Use Lyme

- **Engineering leaders** who want to understand how coding agents actually perform
- **Platform teams** evaluating which agent/tool setup works best for their codebase
- **Researchers** studying coding agent behavior, failure modes, and scaling laws
- **Individual developers** who want a daily copilot that's actually useful

## Who Should NOT Use Lyme

- Teams looking for "set and forget" automation (Lyme is an observability tool first)
- Developers who want maximum task completion at any cost (tradeoffs are explicit)
- Anyone who doesn't care how their coding agent thinks (results-only focus)
